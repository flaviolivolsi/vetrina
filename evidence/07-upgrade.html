  • ABI: Node 18 = 108, Node 20 = 115, Node 22 = 127. node-sass ships prebuilt binaries per ABI; it never shipped one for 127.
  • Migration scope measured on the spike: 34 .scss files — 11 use / as division (→ math.div), 6 rely on @import ordering (→ @use/@forward), 3 override !default variables after import, which dart-sass evaluates in a different order.
  • Replacement is sass@1.77.8 (dart-sass, JS build). Slower cold builds (+~4 s) but no native compile step at all.
  • Verification plan: npm run build:css on both engines, normalise with --style=compressed, diff. Spike showed 2.1 % of selectors differ, all in the ui-kit button and modal partials — needs a human eye, no test covers it.

  • request was archived Feb 2020 and hard-pins tough-cookie@~2.5.0. There is no version of this dependency chain that runs on Node 22 unpatched.
  • The patch is trivial and safe: const isDate = util.types.isDate at the top of cookie.js, three call sites updated. Lives in patches/tough-cookie+2.5.0.patch.
  • Blast radius: every outbound call to the billing provider — invoice sync, checkout webhook replay, refund posting. It throws on the first response with a Set-Cookie header, i.e. immediately, i.e. it would be caught in staging.
  • The proper fix is deleting @acme/billing-client's dependency on request (→ undici). Estimated ~1 week, touches their SDK. Not part of any path here; the patch buys time for it.

The three things that actually decide it

These are judgement calls, not facts — which is why this is your call and not mine.
Can you give up two uninterrupted days in the next 8 weeks?
If yes, A is strictly the cheapest option over any horizon longer than a year. If no — and the Sass diff genuinely needs someone to sit with it — B gets you safe by Friday and costs you 40 wasted minutes.
Do you already run containers in production?
If yes, C is ~3 h, not 7, and is much more attractive. If no, C is not "write a Dockerfile" — it's adopting a registry, an image lifecycle and CVE triage, permanently, to avoid two days of work.
How much do you trust an eyeballed CSS diff?
This is the whole risk of A. 2.1 % of selectors change and we have no visual regression tests. Adding Playwright screenshot tests first would add ~1 day to A and make it near-zero risk.

Effort figures are hands-on engineering hours excluding review and deploy windows. Support dates are from the Node.js release schedule as of this run. Current pin: .nvmrc, package.json#engines and .github/workflows/ci.yml all say 18.20.8 — all three change together in every path.
