# v0 evidence test

The README says: do not build infrastructure until there is evidence that agents
reliably produce pages worth looking at. This is that test.

Ten pages, ten genuinely different tasks. Each was generated by a separate agent with
no shared context, given only the task and the hard constraints: no design kit, no
sight of `examples/build-console.html`, no house style to imitate. That is deliberate.
The question v0 asks is whether an unaided agent produces something good, because the
answer decides whether the next work is a daemon or a kit.

**This rubric was written before any page was generated and before any result was seen.**
Scoring a test you have already peeked at is not a test.

## Rubric

Judged per page. The first one is the only one that really matters; the rest explain a
failure when it happens.

1. **Would you rather read this than the equivalent chat text?** Binary. Not "is it
   pretty", but would you genuinely reach for it. A no here fails the page regardless of
   everything below.
2. **Right shape for the task?** Or is it a console bolted onto a problem that wanted a
   timeline, a map, a comparison? Shape-fit is the thing a general TUI cannot do, so a
   page that gets it wrong has thrown away the entire premise.
3. **Self-contained.** No CDN, no external font, no remote image, no network at render
   time. Any request is an automatic fail, because the phone-with-no-signal case is real.
4. **Legible on a phone**, held one-handed, without pinch-zooming.
5. **State in form, not colour alone.** Position, label, shape, weight. A page that
   only works for people who see colour normally is a broken page.
6. **Restraint.** Did it invent a whole visual language where a plain list would have
   done, or drown the content in chrome?

## Threshold

From the README, fixed in advance:

- **7 or more good → the product is real.** Build the daemon.
- **Around 3 good → the problem is the kit, not the daemon.** Build the kit first and
  re-run this test.
- **Between → look at what separates the good from the bad, and let that decide.**

### The one defect, fixed 3 August 2026

`10-incident.html` overflowed the viewport by 104px at 390px wide. Content-wise it is one
of the strongest pages here. The 19 minutes spent on the wrong cause are drawn as a
physical misalignment between two bands on a shared clock, which is a thing prose cannot
do at all.

**The original diagnosis in this file was wrong, and the correction is worth more than the
fix.** It said the `.two` grid "never collapses to one column, so a 476px panel sits in a
390px viewport", and that "one media query fixes it". `.two` is in fact already mobile
first: it is a plain `display:grid` and only takes two columns above 820px. The media query
was never missing, and adding one would have changed nothing.

Measured by elimination rather than by reading, there were three separate causes:

1. **`.panel` is a grid item**, so it inherited `min-width:auto` and refused to shrink below
   the min-content width of the pre-formatted diff inside it. `min-width:0` lets it shrink;
   the diff already scrolls itself.
2. **A file path in a panel heading.** `services/checkout/src/main/resources/application-prod.yml`
   is one unbreakable word to a browser, widened further by `letter-spacing:.1em`. The panel
   fitted; its heading did not.
3. **A metric name in body text.** `hikaricp_connections_pending`, same problem, which only
   showed below 360px.

Now clean from 280px to 1280px in both themes, with the diff still scrolling inside itself.
The lesson generalises and is the reason `kit.css` exists: **these failures are invisible
to inspection and take seconds to find by measurement.** Reading the CSS produced a
confident wrong answer that survived in this file for two days.

## Read the result honestly

Ten out of ten is a suspiciously good number, and the caveat matters more than the score.

**Each agent was handed an already-structured brief.** "Four root causes: 11 timezone, 6
null-handling, 4 flaky, 2 real" is the analysis already done. So what this test actually
proves is that **agents render structure well when they have it**, which was the open
question about the *kit*, and it is now answered: the kit is not the bottleneck, and it
should be extracted rather than invented.

What it does **not** prove:

- That an agent notices *when* a page beats a paragraph. Every agent here was told to
  build one.
- That an agent can find the structure in a genuinely messy session, rather than render
  structure it was given.
- That anyone opens the window on the second day.

Those are the skill's job, not the kit's, and they stay open. The right conclusion is
narrower than "the product is real": **the taste layer is reachable, the daemon is worth
building, and the remaining risk has moved entirely to the skill.**

## What the good ones had in common

With no coordination between them, the ten converged on these. Counts are stated where
they are not unanimous, because an August 2026 audit found the first version of this list
asserted unanimity it had not measured.

- **A verdict headline, not a topic headline.** "Three import statements cost 228 KB",
  "23 failing tests → 4 causes, 1 is urgent", "The prompt that shipped is not the prompt
  that was written." Seven of the ten led with a finding rather than a subject. *(An
  audit in August 2026 found the original claim of ten out of ten was wrong: three led
  with a topic, and page 09 has no `<h1>` at all.)*
- **A stat strip** directly under the masthead. Four to six tiles, oversized tabular
  number, small caps label. It is the two-second read on every page.
- **Problems before data.** Findings, blockers or "what is wrong" sits above the detailed
  content on nine of ten. Nobody made the reader scroll to learn whether anything is
  wrong.
- **Ordering by urgency rather than by chronology, file order or size.** Page 02 makes
  this explicit: the widest cluster is deliberately not the first one.
- **Redundant state encoding.** A glyph, a spelled-out word, a border style
  (solid / dashed / double / hatched) and a position. Every page did at least three of
  the four, unprompted beyond "do not rely on colour".
- **Monospace for data, proportional for prose.** Paths, numbers, commits and log lines
  in mono; explanation in sans or serif. Unanimous.
- **Progressive disclosure**, in four of the ten: collapsed detail behind `<details>`,
  expand-all controls, filter chips with `aria-pressed`. The glanceable layer stays
  glanceable. *(Originally written as though every interactive page used all three. It
  was not counted at the time.)*
- **A metadata chip row** under the standfirst: branch, commit, counts, timestamp.

That is a design kit, discovered rather than designed. It is written up in
`private/DESIGN-KIT.md`.

## What the bad ones got wrong

There were no bad ones, which is its own finding: with a clear brief and four hard
constraints, the floor is high. The only failures were mechanical rather than editorial:
three narrow-viewport bugs on one page, none of them a missing breakpoint and all three
of the same shape: **something that could not shrink, inside something that could not
scroll.** A grid item with the default `min-width:auto`, and two unbreakable tokens.

That is precisely what a kit can remove, because none of it is a judgement call. `kit.css`
now ships layout primitives with a `min()` floor and no width to set, tables that scroll
inside themselves without a wrapper, and `overflow-wrap:anywhere` on anything monospaced.
An agent cannot reintroduce this class of bug by hand, which matters more than it sounds:
the same defect was misdiagnosed from reading the CSS and sat wrong in this file for two
days before anyone measured it.
