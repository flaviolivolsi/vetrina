POST/api/webhooks/stripe

One inbound webhook touches 6 hops before it is acknowledged, then fans out to 3 independent consumers that Stripe never sees the result of. Two of those consumers write to Postgres; one calls an external API. Below is the whole path, with the two places it breaks.

What is wrong

Both sit on the path below — tap a card to jump to it.

F1 ■ Correctness bug

Signature is verified after the body is parsed

middleware.ts:34 does await req.json(), then line 47 verifies JSON.stringify(body) — a re-serialisation, not the bytes Stripe signed. The payload that gets processed is therefore never the payload that was authenticated, and any whitespace or key-order difference from Stripe flips verification for reasons unrelated to the signature.

→ src/middleware.ts:34–51
F2 ▲ Silent data loss

Analytics consumer has no dead-letter queue

billing-sync and email-notify both call deadLetter(job, err) on failure. analytics-fanout catches and calls logger.warn only, then acks. A failed analytics event is gone — no replay, no alert, no row in stripe:events:dlq.

→ src/workers/consumers/analytics-fanout.ts:41

The middleware owns two gates and then hands off. It also sets x-stripe-event-id and x-stripe-verified: 1 on the forwarded request — headers the route handler trusts blindly (see F1).

⏲GATE 2 · Rate limit ✓ OK src/lib/ratelimit.ts:18 · rateLimit(key) Upstash sliding window, 100 req / 60 s, keyed on the Stripe-Account header. pass → continue · 99.7% 429 rate_limited · ~40/day 4.1 ms p50

One network round-trip to Upstash on every request — it is the single largest slice of edge latency. Keyed per connected account, so a noisy tenant cannot starve the others.

Note: this runs before signature verification, so unauthenticated traffic can burn a tenant's budget. Not flagged as a finding — it is the conventional ordering, and the alternative costs more.

⚿GATE 3 · Signature verification ■ F1 BUG src/lib/stripe/verify.ts:31 · verifyStripeSignature(raw, sig) Called at middleware.ts:47 — 13 lines after the body was already parsed at :34. The verified bytes are a re-serialisation, not the wire bytes. valid → continue 400 invalid_signature · ~6/day 1.2 ms p50 
// src/middleware.ts:31–51
const sig  = req.headers.get('stripe-signature');
const body = await req.json();          // :34  ← stream consumed here
if (body.livemode !== IS_PROD) return json(400, 'env_mismatch');

const key = await lookupSigningSecret(body.account);   // :41

const ok = verifyStripeSignature(JSON.stringify(body), sig, key); // :47
if (!ok) return json(400, 'invalid_signature');

res.headers.set('x-stripe-verified', '1');             // :51

Why it is a real problem, not a nit:

1. JSON.stringify(body) is not byte-identical to what Stripe signed. Key order survives, but Stripe emits "amount":1200 where stringify may re-encode non-ASCII in descriptors (é vs the literal). Those events fail verification and get a 400 — Stripe retries them for 3 days, then drops them.

2. Worse in the other direction: lines 35–41 read body.livemode and body.account and use them to pick the signing secret — before anything is authenticated. An attacker controls which secret their payload is checked against.

Fix shape: read await req.text() once, verify the raw string, and only then JSON.parse it. On Edge the body stream is single-use, so the raw text has to be forwarded to the handler rather than re-read.

  if (req.headers.get('x-stripe-verified') !== '1')     // :16

  const event = await parseEvent(req);                  // :27

Handles 11 event types explicitly and passes the rest through untouched. The runtime split matters: the edge already consumed the body, so parseEvent reads from the re-encoded copy the middleware forwarded.

◻REDIS 5 · Idempotency check ✓ OK src/lib/queue/dedupe.ts:22 · seenEvent(id) SET stripe:seen:<event.id> NX EX 86400 — 24 h window. new → publish · 95.9% 200 duplicate, no-op · 4.1% 2.8 ms p50

Stripe re-delivers aggressively, so the 4.1% duplicate rate is expected. The TTL is shorter than Stripe's 3-day retry ceiling — an event that fails for >24 h and is then re-delivered will be treated as new and re-processed by all three consumers.

Not one of the two headline findings — it degrades loudly (DLQ + a visible unsent receipt) rather than silently. Worth a retry wrapper regardless.

Compare the other two lanes: billing-sync.ts:52 and email-notify.ts:58 both call deadLetter(job, err). This one does not, so a failed event leaves no trace outside a warn log line that nothing alerts on.

Scale of the loss: ~0.4% of analytics jobs hit this catch over the last 7 days — roughly 400 events/week silently missing from analytics_events. Every revenue dashboard built on that table is quietly under-counting.

Fix shape: add deadLetter(job, err) and a analytics_fanout.failed counter, matching the other two consumers.
